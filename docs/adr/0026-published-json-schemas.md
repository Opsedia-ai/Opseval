# ADR-0026: Published JSON Schemas

- **Status:** Proposed
- **Date:** 2026-10-04
- **Deciders:** Opseval maintainers

## Context

Two requirements asked for published JSON Schemas and neither had been met:

- **FR-RPT-02** (M, **v0.1**): "`result.json` (SuiteResult) and JSON Schema for it."
- **FR-CAT-11** (S, v0.2): "Published JSON Schema for scenario and suite files (editor
  autocompletion)."

The architecture is specific — "Pydantic models with JSON Schemas published under
`schemas/v1/`" — and there was no `schemas/` directory. The v0.2 roadmap bullets were all green,
so the gap was invisible from the roadmap; it only showed up by reading the requirement tables.
FR-RPT-02 is a must-have from v0.1.

## Decision

`opseval schemas` generates the schemas from the Pydantic models and writes them to
`schemas/v1/`. Five contracts are published: `scenario`, `suite`, `profile`, `record`, `result`.
Scenario and suite serve editor autocompletion, result is the documented output contract, and
record and profile are published because third parties read and write them.

### The models are the source of truth, and drift is a failure

A committed schema that has drifted is **worse than no schema**: an editor would accept a file
`opseval validate` rejects, or flag a field that is perfectly valid, and the author would trust
the editor. So `opseval schemas --check` fails when the committed files no longer match the
models, with the file named and the fix stated, and it runs in `make check` and in CI. Verified by
adding a field to `Scenario` and watching the check fail.

Rendering is deterministic — sorted keys, fixed indentation, one trailing newline — so
regenerating never produces a spurious diff.

### Generated by alias

`Scenario.schema_` is spelled `schema` in a YAML file. A schema describing the Python field name
would be wrong for every editor that used it, so generation uses `by_alias=True`, and a test
asserts `schema` is present and `schema_` is not.

`extra="forbid"` on the models carries through as `additionalProperties: false`, which is what
makes autocompletion useful: a typo is flagged rather than silently ignored. A test proves the
schemas reject an unknown field, a missing required field, a wrong type, an out-of-range value and
an unknown enum member — a schema that accepts everything would pass "it validates" tests while
being worthless.

### Scaffolded files point at their schema

`opseval init` now writes `# yaml-language-server: $schema=…` at the top of each YAML file, which
is what VS Code and friends look for. Which schema a file follows is only knowable from where it
sits, so the mapping lives in the scaffold writer rather than in the templates: a scaffolded file
pointing at the wrong schema would flag valid fields and accept invalid ones.

A model's own docstring is kept as the schema `description`, with the "generated, do not edit"
note appended. The first implementation spread the generated schema over the note and silently
dropped it for exactly those models that had a docstring; a test parametrised over all five
caught it.

## Consequences

- An editor validates a scenario as it is typed, against the same rules the loader enforces, and
  `result.json` has a documented contract for anyone building on it.
- Every model change now has a second step: run `opseval schemas` and commit. CI says so when it
  is forgotten. That is friction, and it is the price of the schemas being trustworthy.
- The `$id`s point at `https://opsedia.ai/schemas/v1/…`, which **is not served yet**. Editors
  resolve the local file through the `$schema` comment, so autocompletion works today, but the
  URLs are a promise about a host that does not answer. Publishing them is a hosting task, not a
  code one.
- Five schemas are a public contract from now on. `opseval/v1` is meant to be frozen at v1.0
  (FR-CAT-01), so until then a model change can still break a downstream consumer — the schema
  now just makes that visible instead of silent.
- The schemas describe shape, not cross-field rules. `check_references` still catches things a
  JSON Schema cannot express — an unknown scorer id, a `stop_at` that is not a declared
  checkpoint, `security.policy_adherence` without `expectations.policy` — so a file can validate
  in an editor and still be rejected by `opseval validate`. That is the right division, but it
  does mean a green editor is not a guarantee.
